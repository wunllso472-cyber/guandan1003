整理时间：2026-10-07（基于提交 2fdee9f，共 59 次提交；`tsc --noEmit` 无错误，`vitest` 13 个文件 81 个测试全部通过）

---

## 一、架构上做对了的地方

1. **规则和 AI 只写一份，前后端共用**（`shared/`，纯 TS、无依赖）。
   单机在浏览器里跑 `Table`，联机在服务端跑同一个 `Table`，出牌合法性两边一致，测试也只测一份。
   - 分层：`GuandanGame`（纯状态机，只发事件）→ `Table`（计时、托管、AI 座位、暂停）→ `Room`（座位、按座位过滤事件后下发）。
   - 新功能先想清楚放在哪一层：规则放 `game.ts`，“谁来出、什么时候出”放 `table.ts`，“谁能看到”放 `room.ts`。

2. **信息隔离按“该座位本来就能知道什么”来做**。
   - `CardTracker` 每个座位一份，只吃公开事件；托管、困难电脑、提示都只用它，不偷看别人的牌。
   - 服务端下发时过滤：`roundStart` 只给本人手牌；`decision`（含手牌）只发给本人；对家手牌只在自己出完后 `reveal`。
   - 新增任何事件时都要检查：这个事件里有没有别人不该看到的牌。

3. **异步决策用序号丢弃过期结果**（`Table.turnSerial`）。
   每次轮到新的人、暂停时加一；后台模拟回来时序号不一致、已不是这一手、对局结束、牌桌已销毁，就丢弃。
   任何“发出去、过一会儿回来再改状态”的逻辑都应该照这个模式写。

4. **引擎事件里不直接重入调度**：`turn`/`tribute` 事件后用 `queueMicrotask(() => this.schedule())`，等引擎本次调用结束再调度，避免在 `play()` 内部又触发 `play()`。

5. **兜底不卡死**：AI 出牌出错时 `Table.apply` 退回“不出/出最小一张”；模拟线程挂了返回 `null`，改用顾问首选；Jev 超时、置信度低就用本地提示。
   原则：AI 和外部服务的失败只能降低质量，不能让牌局停住。

6. **重计算放到后台线程**：浏览器用 Web Worker（`client/src/game/mcWorker.ts`），服务端用 `worker_threads`（`server/mcWorker.ts`，构建成 `dist/mcWorker.mjs`）。
   开发时 `tsx` 跑 `.ts`、部署时跑打包好的 `.mjs`，由 `import.meta.url.endsWith('.ts')` 区分。

7. **评估开关都以可修改的导出对象出现**（`mcExtra`、`mcLowSample`、`mcInfer`、`mcStage`、`MC_END`/`MC_MID`），默认值保持线上行为，`scripts/bench.ts` 用环境变量切换。
   没采用的实验也保留开关，并在注释里写上评估数字，以后不用重做。

## 二、策略改进的方法（最重要的经验）

1. **只看团队结果**：每局净升级、胜局率、双上率、被双下率；不只看头游率。
2. **配对对打**：同一副牌交换座位各打一次，抵消牌运；结论要带 ± 误差，误差盖过差值就当“没有区别”。
3. **先对弱电脑初筛，最后对强对手验证**：`ai` 跑得快适合初筛；改进最终要对 `auto`（与困难电脑相同）验证，避免只对弱电脑有效。
4. **局数要够**：几百局的差值常在 ±0.1～0.3 级以内，小改动要 2000～4000 局才能看出显著性。
5. **注释里写评估结论**，包括失败的：

| 尝试 | 结果 | 结论 |
|---|---|---|
| 中盘局面评分第二版（加控制牌特征） | 对原电脑 +0.99（第一版 +0.69），对顾问 +0.75（第一版 +0.61） | 采用 |
| 模拟样本不足时、差距 ≥3 倍门槛也采纳 | 托管 40ms 预算 +0.107 ±0.106（800 局）；电脑 +0.029 ±0.011（4000 局） | 采用 |
| 中盘推翻门槛 0.2 / 0.9 | -0.300 ±0.177 / -0.168 ±0.168 | 0.4 已在最好区间 |
| 残局门槛 0.1、残局界限 54 张 | +0.007 ±0.063、+0.040 ±0.107 | 无显著差别，不改 |
| 模拟候选多补 2 个不同牌型 | 对原电脑 -0.17 ±0.13 | 不采用 |
| 模拟拿不准时改用 Jev 排序 | -0.29 ±0.27（200 局） | 不采用 |
| 按“不跟”“跟牌空隙”线索加权猜牌 | 猜牌准确率不升反降（均匀随机约 47.4%） | 默认关闭；印证教材 L05“不跟不是缺牌证明” |
| Jev 采用门槛 0.35 → 0.6 | 300 局对打 | 采用 0.6 |
| 《掼蛋规则与实战技巧》出牌规则（末位负责、防空炸、谁先出炸、炸后要能推进、打下放上）+ 课程牌力评分 | 顾问对停用它们的顾问 +0.034 ±0.018（4000 局）；托管 40ms 预算 −0.065 ±0.145（400 局，看不出差别） | 采用；开关 `courseRules`、`coursePower`，分量 `courseTune` |
| 末位负责分量 0.8/0.4 → 2/1 | +0.036 ±0.017（3000 局） | 采用 2/1 |
| 助攻前期“打上放下”（放下家领牌）计分 | 与主攻一半合计 −0.027 ±0.020（3000 局） | 分量为 0，只作提示理由 |
| 防空炸分量 0.6 → 2.5 | −0.003 ±0.010 | 保持 0.6 |
| 课程牌力评分，坠牌按“小牌且外面压得住”全算 | −0.013 ±0.010（3000 局） | 改为同类有登基牌回收的不算，0.000 ±0.004 |

6. **硬约束和软线索分开**：进贡（进贡者没有比贡牌更大的非逢人配牌）、抗贡（大王在进贡方）是确定信息，作为 `lacks` 硬约束；出牌习惯只是倾向，实测几乎没有信息量。
7. **规则库的 priority 是检查顺序，不是分数**；教材规则是带例外的启发，不能当硬规则。

## 三、排查线上出牌问题的流程

1. 用复盘日志，不凭截图猜：`npx tsx scripts/review.ts [局数]`（密钥 `GD_LOG_KEY` 在 `.env.local`），`--json 文件` 导出原始数据，`--file` 读导出文件。
2. 进行中的局也会实时上传（带 `live`），未执行的托管决策在 `pending`。
3. 日志里看：出牌前手牌、候选排序和分数、模拟样本数与 gain、命中的规则、对三家的推断，判断问题出在顾问评分、模拟、还是规则。
4. 修完写一个能复现该局面的测试（`tests/advisor.test.ts` 里有很多这样的例子），再跑配对评估确认没变差。
5. `/version` 返回线上提交号，先确认线上跑的是哪个版本。

## 四、部署与运维

- Netlify 托管前端（`npm run build:client`），Render 跑联机服务（`render.yaml`，同时提供网页，不依赖 Netlify 也能访问）。
- 前端连接地址靠构建时的 `VITE_WS_URL`；改了环境变量要重新部署才生效。
- 提交信息带 `[skip render]` / `[skip netlify]` 跳过对应平台的自动部署——只改前端或文档时节省构建。
- Render 免费版闲置约 15 分钟休眠，唤醒要几十秒；网页打开时提前发请求唤醒。房间和复盘日志都在内存里，重启即丢，复盘日志靠客户端本地保存后补传。
- 密钥：`JEV_API_KEY`、`DOUBAO_API_KEY`、`GD_LOG_KEY` 只放 `.env.local`（已忽略）和 Render 环境变量；仓库公开，代码里只放日志密钥的 SHA-256。
- Jev 用长连接池（undici `Agent` keepAlive 2 分钟）+ 有对局时定时 `HEAD` 预热，省掉每次约 0.7 秒的握手。

## 五、本次整体 review 发现的问题

按严重程度排序。

### 1. 【严重，已修复】一个畸形 URL 就能让服务端进程崩溃
- 修复：解码失败返回 400；HTTP 回调整体加 `.catch` 兜底（500），单个请求出错不再带崩进程。测试 `tests/server.test.ts` 启动真实服务端进程验证（修复前该测试失败）。
- 经验：`createServer(async ...)` 里任何未捕获的异常都会变成未处理的 rejection，Node 15+ 默认直接退出进程。异步回调一定要有兜底。
- 位置：`server/index.ts:36`，`decodeURIComponent(url.pathname)` 在异步回调里抛 `URIError`，没有捕获，Node 直接退出。
- 复现：`curl "http://localhost:8799/%E0%A4%A"` 之后 `/healthz` 再也连不上，日志为 `URIError: URI malformed`。
- 影响：线上所有房间断开，任何人一个请求就能触发。
- 修法：解码放进 try/catch，失败返回 400；另外给 http 回调整体加 try/catch，并考虑注册 `process.on('unhandledRejection')` 打日志。

### 2. 【中】`/logs` 上传没有任何校验
- 位置：`server/logs.ts`。任何人都能 POST，按 `id` 覆盖已有的局，或刷 500 条把真实记录挤掉（`MAX_ROUNDS = 500`）。
- 建议：至少按 IP 限流；`id` 带客户端随机串，覆盖时校验同一来源；读取密钥放在请求头而不是查询参数（查询参数容易进代理日志）。

### 3. 【中】服务端只有一个模拟工作线程，所有房间排队
- 位置：`server/mcPool.ts`。房间多时请求排队，超过 `budgetMs + 1500` 就返回 `null`，静默退回顾问首选，困难电脑在高峰期悄悄变弱。
- 建议：按 CPU 核数开小池子，或记录超时次数便于发现。

### 4. 【低】Jev 相关的内存与成本
- `server/jev.ts` 的 `lastCall` 按 token 记录、从不清理，长期运行会慢慢增长。
- `ctx` 完全来自客户端，用服务端密钥转发给 Jev；虽然要求在对局中、每 token 2 秒一次，但 token 由客户端自选，可以换 token 绕过限流。可考虑按房间/IP 限流。

### 5. 【低，需确认规则】还贡校验与 AI 选牌不一致
- `game.ts` 的 `returnTribute` 只要求 `rank <= 10`，允许还级牌甚至红桃级牌（逢人配）；`ai.ts` 的 `returnCard` 主动排除了级牌。
- 如果平台规则不允许还级牌/逢人配，引擎应一并拦住；如果允许，保持现状即可。

### 6. 【低】其他
- `Room.setReady` 等处在 `seatOf` 返回 -1 时会抛错，被外层 catch 变成“服务器错误”，没有更明确的提示。
- 服务端的 HTTP、`/logs`、`index.ts` 消息分发没有测试；`room.test.ts` 覆盖了房间逻辑，但入口层没有。
- 仓库根目录放了 `guandan_master_deep_study.docx`、参考图片、`需求.txt`，可以挪到 `docs/` 下，根目录更干净。
- `client/src/scene/TableScene.ts`（929 行）是最大的界面文件，再加功能前可考虑按区域拆分。

## 六、写代码时的约定（沿用现有风格）

- 注释、提交信息、界面文字都用中文；提交信息写“做了什么 + 评估数字”。
- 规则/AI 改动必须配测试；策略改动必须配配对评估结论，写在提交信息和相关注释里。
- 默认值只在评估显著变好时才改；实验功能加开关、默认关闭。
- 新增服务端消息时：参数用 `Number()`/`String()`/`!!` 规整，错误返回中文字符串，由 `reply()` 发回。
